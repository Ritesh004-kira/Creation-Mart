# Master_Goal.md

## Objective

Build, test, and deploy CreatorMatch end-to-end from the five CM-2.0 specifications. Finish **as soon as all mandatory completion criteria pass**. Twelve active implementation hours is the maximum budget, not a planned duration or a reason to keep working after completion.

A static interface, successful build, or submitted deployment job is insufficient. Completion requires a functioning application, real persisted state, authorization checks, browser verification, and a verified deployment outcome. Do not claim perfection without evidence or describe prototype checks as production certification.

Authorization covers coding, selective licensed reuse, dependencies, a suitable implementation branch, canonical migrations, scoped demo data, tests, and eligible demo deployment. ## Execution and efficiency

Read the specifications once, create a short requirement checklist, and start coding. Do not spend the first turn producing another extensive plan.

Protect profiles/portfolios, discovery and briefs first, then complete applications, selection, revisions and delivery. Implement the four defined USPs and all required connected pages.

Batch independent reads/checks. Reuse validated work across turns and compaction. Avoid repeated broad research, redundant tests, speculative features, verbose reports and unnecessary dependency systems. Diagnose repeated failures instead of looping. Do not change the user-selected model or reasoning effort without authorization.

Use these latest checkpoints, advancing sooner whenever possible:
- By hour 6: profiles, portfolios/passports, real discovery, briefs, rights receipts and persistent shortlists.
- By hour 8: complete application-to-revision-to-acceptance workflow.
- By hour 9.5: eligible deployment and live authorization checks.
- Optional AI integration: maximum 30 minutes after the core works.
- Remaining time: necessary regression fixes, responsive/browser checks, demo rehearsal and handoff.

These checkpoints do not authorize waiting, padding work or spending the entire allowance. Complete immediately when the mandatory gates pass. If behind schedule, cut optional AI and decorative extras before required functionality or security.

## Explicit user-requested pause policy

The user explicitly requests changing the actual goal status to **PAUSED** whenever essential user action or confirmation is necessary.

Examples: unavailable login/MFA/OAuth consent or credentials; missing external write/IAM permissions; an irreducibly ambiguous target; unverified potential cash charges; enforced approval rejection; or required external platform approval.

Do not invent confirmation gates for authorized or routine work. Recoverable coding errors and optional-feature failures are handled autonomously. Prepare the concrete reviewable artifact before requesting a final release approval, without performing the gated action.

At a genuine boundary:
1. Save the current checkpoint and completed work.
2. Explain the exact blocker, target and smallest user action needed; name the requirement/source.
3. Report any running billable resources and their automatic expiry. Pausing a goal does not stop AWS resources.
4. Use the available native goal mechanism to set PAUSED and confirm its returned status.
5. Stop all implementation, polling and independent work.

Do not merely announce a pause while leaving the goal active. If the native pause cannot be performed, stop work, report that pause status is unconfirmed, and give the supported manual pause action.

Remain paused until the user explicitly resumes. Then verify the blocker is resolved and continue from the saved checkpoint without repeating completed work.

## Twelve-hour limit

Track actual active implementation time across turns/resumptions, excluding explicit human-wait pauses. Do not infer token/account allowance from hours. Respect native usage and goal limits whenever they stop execution earlier.

No extension beyond twelve active hours is authorized. If unfinished at the limit, checkpoint, report the precise remaining work and request an extension while pausing the goal where the native state permits. A native budget stop takes precedence; never bypass it or mark unfinished work complete.

## Mandatory completion evidence

Verify with actual records and authenticated roles:
creator publication → brand brief publication → discovery and saved shortlist → creator application → brand selection → submission → revision → resubmission → acceptance → private download.

Required evidence includes:
- Meaningful contract, filter/capability-pair, rights and workflow tests.
- Direct API/RPC/Storage negative tests, protected-field attempts, stale versions, idempotency and concurrent selection.
- Every required route and visible action works; refresh/deep links/back navigation retain appropriate state.
- Browser/Playwright verification at 375/768/1440 pixels, keyboard operation and useful loading/error/recovery states.
- Actual deployed readiness, authentication callbacks and full live workflow.
- Genuine model success/failure tests if enabled; otherwise clearly labeled template mode and disabled optional inference.
- Accurate demo-origin/evidence labels, upstream notices, capability ledger and resource/cleanup records.

No mandatory criterion may be silently omitted to meet the deadline. A local fallback is reported as local; it cannot silently substitute for the requested public deployment or justify completion.

## Final handoff and stopping condition

Provide repository/branch/commit, verified deployment URL/status, implemented and disabled features, actual test/browser results, concise demo instructions, secure credential-access location without values, reuse notices, limitations and cleanup/expiry details.

Mark the actual goal **COMPLETE** only when mandatory criteria pass and the authorized deployment outcome is verified. Stop then, even if most of the twelve-hour allowance remains.

Continue through ordinary turn endings until verified completion, an explicitly requested pause condition, or a native budget stop.
